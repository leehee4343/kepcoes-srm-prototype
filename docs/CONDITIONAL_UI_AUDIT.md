# Description 조건부 UI 점검 기록

2026-09-24 / DESIGN_GUIDE v2.60

## 범위와 근거

화면설계 PPTX 12개, 전체 362슬라이드의 Description 텍스트를 추출하여 현재 HTML과 대조했다. 추출 결과는 [DESCRIPTION_UI_RULES.json](DESCRIPTION_UI_RULES.json)에 보존했다. Description 영역이 추출된 슬라이드는 310개이며, 조건·선택 관련 키워드 후보는 137개다. 이 수치는 구현 완료 건수가 아니라 원문 검토를 위한 분류다. 실제 화면 대상 318슬라이드는 독립 페이지 144개와 재사용 팝업으로 구성된다.

사용자 요청에 따라 표시/숨김, 허용 선택지, 입력 활성화, 조건부 필수 표시, 선택 결과 표시, 완료 후 조회 상태를 프로토타입 범위에 포함했다. 서버 저장, 실제 결재·발송, ERP/PMS 연동, 입찰 순위 및 금액 산정은 구현하지 않았다.

슬라이드 번호는 각 원본 PPTX 내부 번호다. 아래 표는 이번에 반영하거나 기존 표시를 보완한 주요 규칙을 묶은 것으로, Description의 모든 업무 요건이 구현됐다는 뜻은 아니다.

방식 전환으로 기존 선택이 허용되지 않으면 허용값으로 정리한다. 숨겨진 텍스트 입력값은 보존하지만 비활성화한다. 세션과 URL에는 열거형 화면 선택값만 전달하며, 입력한 개인정보·금액·첨부파일은 저장하지 않는다. 이는 레코드별 업무 데이터 저장이 아닌 같은 흐름의 화면 시연용 상태다.

## 원문 불일치와 남은 경계

- **일괄 지급조건:** Description의 선금/중도금과 실제 와이어프레임의 선금/준공 표기가 달라 화면의 선금/준공을 채택했다.
- **낙찰하한 관련 조건:** 07-2 슬라이드 57의 방식 설명과 06의 가격유형 선택표가 일치하지 않는 부분은 위 가격유형 표에 따라 예비가일 때 표시했다. 슬라이드 66의 부등호 설명으로 실제 판정 알고리즘을 만들지 않았다.
- **심사/평가 배점:** 제한적 최저가·규격/가격 분리의 Description은 총 배점 45점/최저 30점을 요구하지만 원본 예시 항목 합계는 80점이다. 최저 30점 표시·잠금은 반영했고, 원본 예시 배점은 보존했다. 45점에 맞춘 항목 배분 및 저장 검증은 미구현이다.
- **05·06 품목구성방법:** 규격 표시 조건은 적용했으나 원본 부모 화면에 해당 선택기가 없어 임의로 추가하지 않았다. 기본 품목단가 상태이며, 지정항목 시연은 `ui` 선택값 전달로 가능하다. 04는 실제 선택기로 전환한다.
- **실데이터 조건:** 제출기한·입찰참가 자격·승인 여부·사용자 권한의 실시간 판정, 외부 코드 조회, 개별 업무 건의 전체 상태 추적은 하지 않는다. 원본의 예시 데이터와 화면 내 선택을 사용한다. 소싱분류 하위 코드 데이터 전체는 제공하지 않는다.
- **협력업체 결과 화면:** 내부 낙찰자 선정 화면은 5종 표를 적용했지만 협력업체 결과 화면의 모든 미완료/유찰/재입찰 사례를 실데이터로 재현하지는 않았다.
- 자동 테스트는 DOM의 조건과 상태를 확인한다. 브라우저의 로컬 URL 접근 정책으로 실제 브라우저 렌더링 검증은 수행하지 못했다. 픽셀 배치와 모든 화면 조합을 시각적으로 검증했다는 의미는 아니다.

## 계약·낙찰방법별 조회 사례 보완 (2026-09-24)

- 공통 예시 게시물 17건: 경쟁입찰(일반·제한·지명) × 낙찰방법 5종 = 15건, 수의계약/최저가의 예정가·추정금액 2건. 수의계약과 다른 낙찰방법의 불가능한 조합은 만들지 않는다.
- 발주요청·발주계획·계약현황은 17건, 입찰 전용 목록과 공개 공고는 15건, 수의계약 전용 목록은 2건이다. 관련 대시보드 표에도 해당 업무의 조합을 제공한다. 계약/낙찰방법 열이 없는 요청 목록은 건명에서 사례를 구분한다.
- 공통 스크립트가 기존 표의 열·링크·버튼 구성을 유지하여 예시 행을 채운다. 계약방법·낙찰방법 및 키워드 검색, 초기화, 실제 예시 건수에 따른 페이지 구분과 빈 결과 안내를 제공한다.
- `record` URL 매개변수는 공통 예시의 ID다. 본문 요약·상세·팝업에 선택한 건명과 번호 및 계약/낙찰방법을 반영한다. 상세 탭과 다음 단계, 새 탭 열기에도 ID와 허용 UI 선택값을 전달한다. 같은 화면의 다른 행을 선택하면 해당 사례의 조건으로 재설정하며, 예시 레코드 선택은 신규 입력용 세션 상태에 저장하지 않는다.
- 조회 화면의 지정업체, 제한경쟁 참가자격, 별도 가격투찰 기간, 심사·평가, 종합평가 비율, 현장설명, 제안발표 및 가격유형별 열을 편집 화면과 같은 조건으로 표시한다. 공고 요약 표와 로그인 공고 팝업의 고정 문구도 조건과 연결했다.
- 계약관리의 계획 탭은 수의계약/경쟁입찰별 실제 본문으로 분리했다. 수의계약 본문은 기존 수의계약 계획 조회 화면의 요청기간·배포서류·참여업체·가격·참여서류 구성을 재사용한다.
- 근거: 06 슬라이드 15–18의 허용 조합, 02 슬라이드 25·29–30의 조회 조건, 07-2 슬라이드 10–14의 상세 정보 조건, 08 슬라이드 4의 통합 조회 및 기존 계획 탭의 수의계약 대체 항목 명세.
- 구현: `initPrototypeRecords`, `renderPrototypeRecord`, `initPrototypeRecordSearch`, `initPrototypeReadViews` 및 `initPrototypeConditions`의 게시물 선택 처리.
- 추가 회귀검증: `NODE_PATH=/tmp/srm-ui-test/node_modules node tools/test_prototype_records.cjs`. 조합별 목록, 복합 검색/초기화, URL 전달, 상세 표시, 낙찰 표, 팝업 및 수의계약 계획 전환을 확인한다.
- 실제 Chrome에서 계약현황 17건·2페이지, 수의계약 검색 2건, 상세 선택 및 수의계약 계획 탭의 조건별 본문을 확인했다. 전체 화면과 모든 해상도의 시각 검증을 의미하지는 않는다.
- 본 데이터는 프로토타입 시연용이며 실제 업무 건의 저장, 모든 진행상태 조합, 외부 연동 및 낙찰 계산은 포함하지 않는다.

최종 검증: 기존 144페이지 초기화/659개 단언 및 게시물 연계 991개 단언(합계 1,650개) 통과. JavaScript 문법 검사와 `git diff --check` 통과. 로컬 파일 URL 변경 제한의 대체 경로와 이전 URL 선택값이 섞이지 않는 새로고침도 검증했다.
